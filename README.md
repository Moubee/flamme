## Introduction
Elsa is a powerful workflow library that enables workflow execution within any .NET application. Elsa allows you to define workflows in various ways, including:

- Writing C# code
- Using a separately hosted visual designer
- Specifying workflows in JSON

![Workflow authored in a separately hosted visual designer](./design/screenshots/http-hello-world-workflow-designer.png)

### Try with Docker

This repository builds the workflow server and backend libraries. To try the reference server, build and run its Docker image from the repository root:

```shell
docker build -f docker/ElsaServer.Dockerfile -t elsa-server:local .
docker run --rm -it \
  -e ASPNETCORE_ENVIRONMENT=Development \
  -e HTTP_PORTS=8080 \
  -e HTTP__BASEURL=http://localhost:13000 \
  -p 13000:8080 \
  elsa-server:local
```

The server exposes a health check at `http://localhost:13000/health/live` and management APIs under `http://localhost:13000/elsa/api`. The reference application is intended for development. Studio hosting and deployment artifacts are no longer included; [Elsa Studio](https://github.com/elsa-workflows/elsa-studio) must be hosted separately if you need a visual designer.

For any non-development deployment, inject a secure random JWT signing key through environment variables or a secrets manager instead of using committed appsettings values. For code-first hosts such as `Elsa.Server.Web`, set `Identity__Tokens__SigningKey`. For shell-based hosts, set the shell feature key, for example `CShells__Shells__Default__Features__Identity__SigningKey`.

The Development configuration includes sample identity users and applications. For other environments, configure your own API credentials through environment-specific identity configuration or a secret manager; see the [server configuration notes](src/apps/Elsa.Server.Web/README.md#secrets).

### TLS and custom certificate authorities

All Elsa Docker images now ship with the operating system's certificate authority bundle baked in at build time. This means you can call public HTTPS endpoints such as `https://example.com` without any additional configuration.

If you need to trust a private or corporate CA, mount the certificate bundle into the container and reference it via `EXTRA_CA_CERT`:

```bash
docker run \
  -e ASPNETCORE_ENVIRONMENT=Development \
  -v /path/to/company-ca.crt:/certs/company-ca.crt:ro \
  -e EXTRA_CA_CERT=/certs/company-ca.crt \
  elsa-server:local
```

On startup, the container copies the certificate into `/usr/local/share/ca-certificates` and runs `update-ca-certificates`, making the trust available to .NET, OpenSSL, curl, and other system components. Multiple certificates can be provided by pointing `EXTRA_CA_CERT` at a directory containing `.crt` or `.pem` files.

In highly restricted environments where you cannot modify the system trust store, you can instead rely on the standard `SSL_CERT_FILE` or `SSL_CERT_DIR` environment variables:

```bash
docker run \
  -e ASPNETCORE_ENVIRONMENT=Development \
  -v /path/to/company-ca-bundle.pem:/certs/custom.pem:ro \
  -e SSL_CERT_FILE=/certs/custom.pem \
  elsa-server:local
```

> ℹ️ Installing the CA bundle adds roughly 300KB to the Debian-based images. No package managers run at container startup; all trust updates happen immutably at build time or via the mounted certificates shown above.

## Supported .NET Versions

Libraries and app hosts support .NET 10 and .NET 11. .NET 8 and .NET 9 are no longer supported. Development requires the .NET 11 SDK selected by `global.json`; install the .NET 10 runtime to run both test targets.

Repository Dockerfiles build with the .NET 11 SDK and run on .NET 11 by default. Pass `--build-arg DOTNET_RUNTIME_VERSION=10.0` to `docker build` to create a .NET 10 image.

## Features

Elsa offers a wide range of features for building and executing workflows, including:

- Execution of workflows in .NET 10 and .NET 11 applications.
- Support for both short-running and long-running workflows.
- A programming model loosely inspired by Windows Workflow Foundation.
- Support for workflows authored in separately hosted visual designers.
- Native support for activity composition, including activities like `Sequence`, `Flowchart`, and `ForEach`.
- Parallel execution of activities.
- Built-in activities for common scenarios, such as sending emails, making HTTP calls, scheduling tasks, sending and receiving messages, and more.
- Workflow versioning and migration via API.
- Easy integration with external applications via HTTP, message queues, and more.
- Actor model for increased workflow throughput.
- Dynamic expressions with support for C#, JavaScript, Python, and Liquid.
- Persistence through PostgreSQL with Entity Framework Core or the built-in in-memory stores. See the [migration guide](doc/postgres-inmemory-migration.md) for removed providers.
- [Elsa Studio](https://github.com/elsa-workflows/elsa-studio): a separately maintained and hosted Blazor app for managing and designing workflows.

## Use Cases

Elsa can be used in a variety of scenarios, including:

- Long-running workflows such as order fulfillment and product approval.
- Short-running workflows such as sending emails and generating PDFs.
- Scheduled workflows such as sending daily reports.
- Event-driven workflows such as sending welcome emails when a user signs up.

## Coding Workflows

Elsa allows you to define workflows in code using C#. The following example shows how to receive HTTP requests and send an email in response:

```csharp
public class SendEmailWorkflow : WorkflowBase
{
    protected override void Build(IWorkflowBuilder builder)
    {
        builder.Root = new Sequence
        {
            Activities =
            {
                new HttpEndpoint
                {
                    Path = new("/send-email"),
                    SupportedMethods = new(new[] { HttpMethods.Post }),
                    CanStartWorkflow = true
                },
                new SendEmail
                {
                    From = new("alic@acme.com"),
                    To = new(new[]{ "bob@acme.com" }),
                    Subject = new("Your workflow has been triggered!"),
                    Body = new("Hello!")
                }
            }
        };
    }
}
```

## Contributing

We welcome contributions from the community and are pleased that you are interested in helping to improve the Elsa Workflow project! Here are the steps to contribute to our project:

### 1. Fork and Clone the Repo
To get started, you'll need to fork the repository to your own GitHub account. You can do this by navigating to the [Flamme GitHub repository](https://github.com/DenDeline/flamme) and clicking the "Fork" button in the top-right corner of the page. Once you have forked the repo, you can clone it to your local machine using the following command:

```bash
git clone https://github.com/YOUR_USERNAME/flamme.git
```
Replace `YOUR_USERNAME` with your GitHub username. For more information on forking a repo, check out the GitHub documentation [here](https://docs.github.com/en/github/getting-started-with-github/fork-a-repo).

Incorporating the details about the "apps" folder and its projects into the second point about opening the `Elsa.slnx` using your favorite IDE, we can expand the instructions to guide developers on where to start and what projects they might want to explore first. Here's an updated version of that section with the additional information:

### 2. Open `Elsa.slnx` Using Your Favorite IDE
After cloning the repository, navigate to the cloned directory and open the `Elsa.slnx` solution file with your preferred IDE that supports .NET development, such as Visual Studio, JetBrains Rider, or Visual Studio Code with the appropriate extensions.

Within the solution, the "apps" folder includes these reference server applications:

- **Elsa.Server.Web**: This project is a reference ASP.NET Core application that acts as a workflow server. It's a great starting point if you want to understand how Elsa functions as a server-side workflow engine.

- **Elsa.ModularServer.Web**: A shell-based workflow server with configuration-driven features and package loading.

- **Elsa.Server.LoadBalancer**: A reverse proxy configured through YARP.

### 3. Submit a PR with Your Changes
Once you have made your changes, commit them and push them back to your fork. Then, navigate to the [Flamme repository](https://github.com/DenDeline/flamme) and create a new Pull Request. Ensure your PR description clearly describes the changes and any relevant information that will help the reviewers understand your contributions. For a detailed guide on creating a pull request, visit [Creating a pull request from a fork](https://docs.github.com/en/github/collaborating-with-issues-and-pull-requests/creating-a-pull-request-from-a-fork).

### 4. Open an Issue First
Before you start working on your changes or submit a pull request, please open an issue to discuss what you would like to do. This step is crucial as it ensures you don't spend time working on something that might not align with the project's goals or might already be under development by someone else. You can open an issue [here](https://github.com/DenDeline/flamme/issues).

This approach helps us streamline contributions and ensures that your efforts are aligned with the project's needs and priorities. We look forward to your contributions and are here to support you throughout the process. Thank you for contributing to the Elsa Workflow project!
